How the analysis pipeline works

This page covers the data and software side of the analysis of a 20-year, storm-resolving climate projection (TCo2559, about 4–5 km, 2020–2039) on HEALPix grids. The simulation itself was produced within the Destination Earth project; this work is the analysis. The page shows how very large GRIB and NetCDF output is read in chunks with Dask, reduced step by step from hourly fields to 5-year means and trends, and saved as small compressed files that the figures are drawn from.

3. Problems the pipeline had to solve

data volume

Too big for memory

One variable over 20 years at km scale does not fit in RAM. Fields are opened lazily with Dask chunks, and nothing is loaded until a reduction asks for it.

chunking

Chunks match the question

For time statistics at each pixel, time is one chunk and pixels are split ({'time': -1, 'values': 10000}). For time reductions, short time chunks are used instead (for example 744 hours, one month).

memory

A fixed memory budget

A local Dask cluster with 4 workers and 12.5 GB each keeps the job inside a 50 GB memory budget, so Dask spills to disk instead of running out of memory.

grids

HEALPix without metadata

The files do not always say which HEALPix level they use. NSIDE is worked out from the number of pixels (for example 196,608 pixels = NSIDE 128, nested order) before any coordinate is computed with healpy.

formats

GRIB and NetCDF together

Atmospheric output is GRIB, read with cfgrib; ocean output from FESOM is NetCDF on its own NG5 mesh. Both end up as xarray objects with the same handling.

repository size

GitHub's 50 MB limit

Outputs of two notebooks were too large. They were cleared and a curated set of figures was added back, so the notebooks stay readable on GitHub.

4. What could come next

IdeaWhy
Shared HEALPix helpersNSIDE inference and HEALPix-to-lat-lon regridding repeat across notebooks. One tested module would remove the copies.
Tests and CIThere are no automated tests yet. A small synthetic HEALPix field would let the reduction and regridding code be checked on every push.
Zarr outputWriting the derived fields as chunked Zarr would allow cloud access and partial reads instead of whole NetCDF files.
Batch jobsThe reduction steps could run as Slurm jobs from a script, so the notebooks are only used for plotting.

5. In one sentence

Hourly km-scale GRIB and NetCDF output on HEALPix grids is read lazily with Dask under a fixed memory budget, reduced step by step to monthly, annual and 5-year statistics, saved as compressed NetCDF, and only then turned into maps, trends, heatwave counts and tracked cloud and rain features.
